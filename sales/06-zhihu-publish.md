## 从 demo 到生产，差了一个「谁负责」

多 Agent 系统这两年从演示阶段进入了生产环境。CrewAI、AutoGen、LangGraph，以及我们自己维护的 Hermes 多 profile 协作，都在承担真实任务。演示环境下故障后重启即可恢复，生产环境则必须回答三个问题：哪个环节触发的、为什么发生、消耗了多少成本。

第三个问题最容易被忽略，也最难回答。Agent 每轮调用都在产生 token 消耗，会话上下文持续增长，任务拆分不断细化，月底核算时成本去向往往无从追溯。我们最初开发 agentlens-audit，起因正是这个：不是想做一个「AI 审计平台」，而是想厘清自己系统内的实际行为与成本结构。

下文先介绍这个项目做了什么，再展开我们在实现过程中遇到的关键问题与对应设计。多 Agent 审计这个方向，目前还没有成熟的行业方案，希望这些经验能带来一些参考价值。

## agentlens：为多 Agent 系统设计的审计工具

### 项目定位

agentlens 是一个开源的多 Agent 系统审计工具，回答四个问题：发生了什么、该不该发生、谁负责、怎么改。观测工具（如 Langfuse、LangSmith、OpenTelemetry）记录行为轨迹，回答「发生了什么」；审计工具判断行为是否应该发生、责任归属与改进方向。两者解决的是不同层次的问题，可以共存：观测管事实，审计管判断。

### 核心能力：七层审计

审计按七个维度分层展开，覆盖从过程还原到治理落地的完整链条：

- Graph 协作图谱：还原任务链路与事件依赖，回答「发生了什么」
- Evidence 证据链：每条结论附带可回溯的证据锚点
- Decision 决策审计：核查审批链与授权流程（批准者、合规性）
- Shadow 影子智能体：识别未登记的 Agent 与未授权的工具调用
- Compliance 权限合规：执行用户决策 / 用户授权 / 自主决策三分法
- Cost 成本治理：token 浪费归因到具体 Agent 与事件
- Gate CI 门禁：违规超阈值映射为非零退出码，阻断流水线

七层不是七个独立模块的堆叠，而是一条递进链：过程可见 → 可问责 → 可治理。后面会展开说明这层逻辑。

### 使用方式与形态

安装与使用都很轻：

- 安装：pip install agentlens-audit
- 输入：gateway 日志或统一 JSONL 事件流
- 输出：HTML 审计报告（KPI 卡、严重度分布、Top10 浪费、证据与修复建议）
- 扩展形态：MCP Server（7 个工具，供 Agent 直接调用审计能力）、Web 仪表盘

技术实现上，项目坚持零第三方运行时依赖，核心全部使用 Python 标准库（≥3.9）。这带来两个直接好处：任何环境都能直接运行，无需处理依赖冲突；审计结论的确定性不受运行环境影响（后面「审计确定性」一节会展开）。

## 设计过程中遇到的三个关键问题

### 异构日志，缺乏统一的事件模型

第一个问题是日志格式。Hermes 的 gateway.log 与 agent.log 是两套格式，CrewAI 提供 event stream，AutoGen 记录 conversation。字段命名、记录粒度、时间戳语义各不相同。审计的第一步不是编写检测规则，而是将异构日志归一化为统一的事件模型。

难点在于抽象层设计。事件需要保留足够的细节信息（调用方、工具、输入输出规模、上下文增量），同时不能绑定任何特定框架的术语。CrewAI 的 task、Hermes 的 session、AutoGen 的 agent_run，语义上都对应「一次任务执行」，在事件模型中应当是同一实体。

我们的方案是定义统一的事件流 schema（JSONL），为每个框架实现一个转换器（converter），将原始日志翻译为标准事件。审计核心只依赖该 schema，不感知任何框架的原始格式。新增框架的接入成本因此被压缩为「编写一个转换器」，审计逻辑无需改动。这个设计在后续实践中验证了价值：我们在同一环境中同时接入了 Hermes 主 profile 与 researcher profile 的日志，两种格式，一套审计管线。

### 异步并发下，时间序无法还原因果序

第二个问题更隐蔽。Agent 协作并非线性执行：一个任务拆分为多个子任务并行运行，期间存在回调、等待与超时重试。按时间戳排序得到的是一条混合事件流，不同会话的事件相互穿插，复盘时难以判断每个事件的归属。

我们的生产环境曾出现过这样的情况：一条任务链中混入 3 个不同 profile 的会话，按时间排序后，A 会话的中间结果被 B 会话误作输入引用。

审计需要还原的是因果序而非时间序：哪个事件触发了哪个事件，哪个输出成为哪个输入。实现上我们做了两层处理：按会话（session）隔离事件，在会话内按事件引用链（evidence refs）重建依赖关系。每条 finding 都附带证据锚点（事件 ID 加位置），可以回溯到完整上下文。缺少这一层，审计结论就无法支撑争议仲裁。

### token 成本归因：增量成本归属如何判定

第三个问题是成本核算。token 成本不是简单的「谁调用谁付费」：输入与输出计价不同，缓存命中存在折扣，上下文膨胀产生隐性成本。一个会话从 10 万 token 增长到 20 万，多出的 10 万该归因于什么？

是 prompt 设计的问题，是工具输出注入过大，还是任务本身未拆分？归因错误会直接误导治理方向：该调整阈值的情况去修改了 prompt，该拆分任务的情况去调整了阈值。

成本模型我们做了细分：输入输出分开计价，缓存读写按实测折扣计入（我们环境中的缓存命中率为 98-99%，cache read 按 0.10 元/M 计），浪费检测按类别归因：大输出注入、重复调用、上下文膨胀，每类对应独立算法。上下文膨胀进一步区分两种情形：「压缩机制未触发」与「压缩后仍无效」。前者应调整阈值，后者应拆分任务，判断错误都会导致治理方向偏离。

## 为什么是「七层」：一条递进链

早期版本按检测项组织：发现、成本、合规……每增加一个需求就新增一个模块，最终成为一个功能堆叠。后来我们重新梳理，审计的本质是一条递进链：

过程可见 → 可问责 → 可治理

- 过程可见：Graph 协作图谱还原任务链路，Evidence 证据链保证每条结论可回溯。先明确发生了什么、如何发生。
- 可问责：Decision 决策审计核查审批链（批准者、流程合规性），Shadow 影子智能体识别未登记的 Agent 与未授权的工具调用，Compliance 权限合规执行用户决策 / 用户授权 / 自主决策三分法。明确问题之后，界定责任归属。
- 可治理：Cost 成本治理将浪费归因到具体 Agent 与事件，Gate CI 门禁将「违规超阈值」映射为非零退出码，直接阻断流水线。回答如何阻止问题再次发生。

七层对应三个递进问题。报告布局也遵循该逻辑：KPI 卡（发现总数 / 预估浪费 / 影子 Agent / 审批绕过 / 可避免占比 / 闭环率）置于顶部，严重度分布与 Top10 浪费居中，证据与修复建议置底。

## 几个值得展开的技术细节

### 转换器插件架构

统一事件流是核心抽象。converters/ 目录下每个转换器对应一个框架，输出统一 schema。审计核心不 import 任何框架的库，只消费 JSONL。这一约束保证了审计逻辑的纯净性，同时将新框架接入简化为「编写转换器 + 运行测试」两个步骤。

### 审计确定性

相同输入必然产生相同输出，包括成本数字。cache 折扣口径与价格常量固化在模型中，报告标注计算口径。这一点对争议仲裁至关重要：「该 finding 的浪费金额是否可信」，如果更换运行环境数字就发生变化，结论将无法作为依据。

### 防篡改：报告本身也需被审计

审计报告作为治理依据，其自身可信度如何保证？我们实现了 SHA-256 文档哈希链：每份报告计算内容哈希，verify 时重新计算比对，任何字节级修改都会立即报错。归档报告作为证据使用时，这一机制不可省略。

### 合规条款与 finding 的映射

网信办《智能体规范应用与创新发展实施意见》于 2026 年 5 月发布，EU AI Act、OWASP LLM Top 10 2026 与 Agentic Top 10 均将 Agent 决策链路列为审计对象。法规映射并非将法条原文抄入报告，而是将 finding 的 title 模式关联到具体条款：一条 finding 生成时，自动附带其可能违反的条款与整改要求。我们维护了 439 条映射，覆盖网信办《实施意见》/ EU AI Act / 《拟人化互动办法》/ OWASP 两套 Top 10 / ACS 2026。映射表支持人工修正，审计发现与法规不对应时允许标注纠正，人工判定优先于静态表。

## 落地验证

以上设计在真实环境中运行了 30 天，数据如下：

- 单日审计 1191 条 findings（high 70 / medium 972 / info 149），预估可避免浪费 39.03 元
- 可避免成本浪费占比 63-76%，主要构成为会话上下文膨胀、大输出注入、重复调用
- 治理后 bloat findings 从 66 条降至 30 条，浪费金额从 391 元降至 35 元区间
- 完整审计 11268 事件，产出 727 findings，验真通过，合规映射 0 unknown
- 325 个测试全绿，覆盖七层审计全部逻辑

这些数字验证了设计的有效性，而非用于展示成果。每个数字背后都对应一类问题的收敛过程：以 bloat 为例，从发现 66 条到降至 30 条，中间经历了调整压缩阈值、拆分长任务、在会话边界增加主动重置等步骤，每一步都由审计报告指出方向、人工确认后执行。

## 多 Agent 审计：一个尚未成熟的领域

多 Agent 审计目前没有行业标准。事件模型如何统一为规范？成本归因的粒度应到哪一层？Agent 自主决策的边界能否通过审计有效约束？这些问题我们仍在探索。

工具已开源：github.com/waiky-github/agentlens-cli，可安装试用（pip install agentlens-audit）。如果你也在运行多 Agent 系统，欢迎到 GitHub 提交 issue，分享你遇到的审计场景。
